# EC Public Key tests


## Motivation

An elliptic curve (EC) public key over a prime field $\mathbb{F}_p$ is a point
$P = d \cdot G$ on an elliptic curve $y^2 \equiv x^3 + a x + b \pmod{p}$,
where $G$ is a base point of prime order $n$ and $d \in [1, n - 1]$ is the
secret private key. While computing the discrete logarithm $d$ of a valid,
uniformly random point $P$ on a strong curve is intractable, implementation
flaws in key generation or curve selection can introduce severe weaknesses:

*   **Invalid points or curves:** A public point $P$ that does not lie on the
    curve or in the prime-order subgroup generated by $G$ may indicate a
    corrupted key or an active invalid-curve / small-subgroup attack [BiMeMv].
*   **Weak curves:** Curves with small subgroup order $n < 2^{224}$ (offering
    less than 112 bits of security) or binary-field curves (`sect*`) subject to
    algebraic attacks [Semaev] provide insufficient security margins.
*   **Low-entropy or structured private keys:** Bugs in random number generation
    or buffer initialization—such as setting only a single 32-bit word of $d$
    or repeating the same 32-bit word across $d$ [ethercombing]—reduce the
    effective key space to $2^{32}$, allowing the private key to be recovered
    via batch Baby-Step Giant-Step (BSGS) search.
*   **Predictable or unseeded PRNGs:** System-level entropy failures—such as the
    Debian/Ubuntu OpenSSL PRNG vulnerability [CVE-2008-0166] [YilekEtAl],
    unseeded or default-seeded non-cryptographic PRNGs, or all-zero and
    placeholder seed buffers [HDWH12]—collapse key generation into a small
    deterministic set of private scalars whose public keys can be detected in
    constant or logarithmic time with exact discrete-logarithm recovery.
*   **Related private keys:** If a broken PRNG or counter generates multiple
    private keys that differ by a small offset $k = d_1 - d_2$, the relation
    $P_1 - P_2 = k \cdot G$ can be detected across a batch of public keys.

## Batch Elliptic Curve Arithmetic

Because testing millions of EC keys individually would be prohibitively slow,
`ec_util.py` and its C++17 `pybind11` extension (`cc_util/ec_batch`) implement
batch elliptic curve arithmetic in affine coordinates using Montgomery's
simultaneous modular inversion trick [BosEtAl]:

*   **Simultaneous Inversion (`BatchInverse`):** The modular inverses of $N$
    field elements are computed using a single modular inversion and
    $3(N - 1)$ modular multiplications.
*   **Affine Batch Addition (`BatchAdd`, `BatchAddX`, `BatchAddSubtractX`):** By
    inverting all $x$-coordinate differences $x_P - x_{Q_i} \pmod p$ in a
    single `BatchInverse` call, computing the $x$-coordinates of both
    $P + Q_i$ and $P - Q_i$ requires only 2.5 modular multiplications and 1
    modular squaring per point.
*   **C++ GMP Engine (`EcBatchEngine`):** For odd prime moduli (covering all
    supported NIST, `secp256k1`, and Brainpool curves), batch
    discrete-logarithm searches execute in C++ over GMP (`libgmp` / `mpz_class`)
    and release the Python GIL, falling back to pure Python if unavailable.

## Single Key Checks

### CheckValidECKey

Verifies that each EC public key $P = (x, y)$ is mathematically valid
(`SEVERITY_MEDIUM`):

1.  **Supported prime-field curve:** The curve must be a known prime-field curve
    in `ec_util.CURVE_FACTORY` (`secp192r1`, `secp224r1`, `secp256r1`,
    `secp384r1`, `secp521r1`, `secp256k1`, `brainpoolP256r1`, `brainpoolP384r1`,
    or `brainpoolP512r1`). Unknown curves and binary-field curves (`sect163k1`,
    `sect233k1`, `sect283k1`, `sect409k1`, `sect571k1`, `sect163r2`,
    `sect233r1`, `sect283r1`, `sect409r1`, `sect571r1`) are rejected.
2.  **Not the point at infinity:** $P \neq \mathcal{O}$.
3.  **Valid field coordinates:** Both coordinates satisfy $0 \le x < p$ and
    $0 \le y < p$.
4.  **Curve equation:** The coordinates satisfy the short Weierstrass equation
    $y^2 \equiv x^3 + a x + b \pmod{p}$.
5.  **Subgroup membership:** If the curve cofactor $h > 1$, the check verifies
    that $n \cdot P = \mathcal{O}$ so that $P$ lies in the prime-order
    subgroup generated by $G$.

### CheckWeakCurve

Checks whether the key uses a curve whose base-point order $n$ has bit length
less than 224 bits (`curve.n.bit_length() < 224`, such as `secp192r1`), where
Pollard's rho algorithm can compute discrete logarithms in significantly fewer
than $2^{112}$ operations. Keys on such curves are flagged with
`SEVERITY_MEDIUM`.

### CheckWeakECPrivateKey

Checks whether the private key $d$ (where $P = d \cdot G$) has one of the
following low-entropy structures modulo $n$ (`SEVERITY_CRITICAL`), motivated
by weak keys discovered in the wild [ethercombing]:

1.  **Single 4-byte window set in a `0x00`-padded buffer:** Only 4 contiguous
    bytes (at byte-aligned offset $0 \le 8j \le \text{byte_bits}(n) - 32$) or
    the 32 most significant bits (offset $\text{bit_length}(n) - 32$ when
    $\text{bit_length}(n)$ is not a multiple of 8, such as `secp521r1`) are
    non-zero:

$$d \equiv u \cdot m_j \pmod{n} \quad (0 \le u < 2^{32}).$$

2.  **Single 4-byte window in a `0xff`-padded buffer or sign-extended negative
    32-bit integer:** All bits outside a 32-bit window $m_j$ remain `0xff`
    (for example from an erased flash page or `memset(..., 0xff, ...)` buffer
    followed by a partial 4-byte RNG write, or two's-complement sign extension
    of a negative `int32_t` across $B = 2^{\text{bit_length}(n)} - 1$ or
    $B = 2^{\text{byte_bits}(n)} - 1$):

$$d \equiv B - u \cdot m_j \pmod{n} \quad (0 \le u < 2^{32}).$$

3.  **Negative 32-bit integer reduced modulo $n$:**

$$d \equiv -u \pmod{n} \quad (0 < u < 2^{32}).$$

4.  **Repeated 32-bit words:** The private key consists of a constant 32-bit
    word $u$ repeated $w$ times
    ($2 \le w \le \lceil \text{bit_length}(n) / 32 \rceil$):

$$d \equiv u \cdot \sum_{k=0}^{w - 1} 2^{32k} \pmod{n} \quad (0 < u < 2^{32}).$$

Rather than running a separate search for each candidate structure,
`ExtendedBatchDL` algebraically reduces every form to solving discrete
logarithms $u \in [0, 2^{32})$:

*   Forms (1) and (4): $Q_{P,j} = m_j^{-1} P = u \cdot G$.
*   Form (2): $m_j^{-1}(B \cdot G - P) = C_{B,j} - Q_{P,j} = u \cdot G$,
    reusing $Q_{P,j}$ via a single affine `BatchAdd` with precomputed curve
    constants $C_{B,j} = (B \cdot m_j^{-1} \bmod n) G$ and zero extra scalar
    multiplications.
*   Form (3): $-P = u \cdot G$.

1.  **Chunked point precomputation:** Input keys are processed in bounded
    chunks. For each key $P$, `ExtendedBatchDL` computes $m_j^{-1} P$ using
    a precomputed width-2 non-adjacent form (NAF) addition chain for the
    repeated-word multipliers, any non-byte-aligned MSB multiplier, and the
    highest byte-shift multiplier, while deriving all remaining byte-shifted
    points $(2^{8j})^{-1} P = 2^8 \cdot (2^{8(j+1)})^{-1} P$ via 8 Jacobian
    point doublings per step, followed by `BatchJacobianToAffine`.
2.  **Bounded-memory multi-target BSGS (`BatchDL`):** Given
    $M = \text{#forms} \cdot \text{#keys}$ target points and search bound
    $2^{32}$, `BatchDL` builds a compact hash-keyed baby-step table of
    $x$-coordinates of $b \cdot G$ for
    $0 \le b < T = \min(T_{\max}, \lfloor \sqrt{M \cdot 2^{31}} \rfloor)$
    (exploiting $x(-Q) = x(Q)$ so each entry covers $\pm b$) and takes giant
    steps of size $t = 2T - 1$ using batched simultaneous inversions. In the
    C++ engine (`cc_util/ec_batch`), both point precomputation and BSGS run
    without materializing intermediate Python point lists, partitioning the
    baby-step table into L2-resident slices of `6`-byte open-addressed slots
    (`16`-bit tag + `32`-bit index). For typical batches ($T < T_{\max}$), the
    time and memory complexity is

$$O\left(\sqrt{\text{#forms} \cdot \text{#keys} \cdot 2^{32}}\right).$$

When a discrete logarithm $u$ is found, the corresponding private scalar $d$
is reconstructed modulo $n$, verified on the curve, and attached to the test
result.

### CheckOpensslDenylistEC

Checks whether an EC public key $P = (x, y)$ was generated by Debian or
Ubuntu's crippled OpenSSL `0.9.8c`–`0.9.8g` pseudo-random number generator
(`SEVERITY_CRITICAL`) [CVE-2008-0166] [YilekEtAl]. Between September 2006 and
May 2008, two `MD_Update` lines in `crypto/rand/md_rand.c` were commented out to
silence Valgrind warnings, leaving `ssleay_rand_bytes` dependent solely on:

1.  **Process ID:** The 15-bit Linux process ID $\text{pid} \in [0, 32767]$.
2.  **Architecture ABI:** Word size (`sizeof(long)`) and byte order (`32-bit
    little-endian`, `64-bit little-endian`, or `32-bit big-endian`).
3.  **Pre-seeding state:** Standard CLI / OpenSSH initialization without a state
    file (`RAND_status`), with a 1024-byte `~/.rnd` file (`RAND_load_file`),
    with an empty `/dev/null` state file, or a direct C API call to
    `EC_KEY_generate_key`.

Across the 12 `(architecture, seeding_mode)` configurations and 32,768 PIDs,
each affected prime curve has at most $12 \times 32{,}768 = 393{,}216$ weak
keys. By default, `openssl_denylist_ec.lzma` covers `secp256r1`, `secp384r1`,
and `secp521r1` (`secp192r1`, `secp224r1`, and `secp256k1` are currently omitted
to save space and memory) and stores a sorted table of 32-bit $x$-coordinate
suffixes (`x mod 2^32`) paired with 19-bit `(config_index, pid)` metadata:

1.  **Fast filtering:** Binary search (`bisect_left`) checks `x & 0xffffffff` in
    $O(\log M)$ time, rejecting over $99.99\%$ of non-weak keys without any
    elliptic curve operations.
2.  **Exact reconstruction and verification:** On any 32-bit suffix match,
    `debian_openssl_generator.generate_ec_private_key` replays the exact
    OpenSSL 0.9.8 `bn_rand_range` state machine to recover the candidate
    scalar $d$ and verifies $d \cdot G = P$ on the curve. This guarantees
    a zero false positive rate and attaches the recovered discrete logarithm
    $d$ to the test result.

### CheckUnseededRandEC

Checks whether an EC public key $P = (x, y)$ was generated from an unseeded /
default-seeded PRNG or a deterministic zero / weak seed (`SEVERITY_CRITICAL`),
analogous to `CheckUnseededRand` for RSA [HDWH12]. By default,
`unseeded_rands_ec.lzma` covers `secp256r1`, `secp384r1`, and `secp521r1`
(`secp192r1`, `secp224r1`, `secp256k1`, and `brainpoolP256r1`–`brainpoolP512r1`
are currently omitted to save space and memory):

*   **Unseeded and default-seeded PRNGs:** Initial outputs of GMP
    (`mpz_urandomb` / `mpz_urandomm` across Mersenne Twister and
    `gmp_randinit_lc_2exp_size` linear congruential generators), Go `math/rand`
    (default `Seed(1)` and small seeds across Go `< 1.20` and `1.20+`
    `crypto/ecdsa` and `crypto/elliptic` key generation), C++ `std::mt19937` and
    `std::mt19937_64` (default seed `5489` and small seeds), Python
    `random.Random`, Java `java.util.Random`, and C `glibc` / BSD / MSVC
    `rand()`.
*   **Zero, repeated-byte, and weak-seed derivations:** Direct constant or
    sequential byte patterns, and cryptographic derivations (`SHA-1`, `SHA-256`,
    `SHA-384`, `SHA-512`, `SHAKE-256`, `HMAC-SHA256`, `HKDF-SHA256`, and
    `BIP-32` root key generation) applied to empty, all-zero (`0x00`),
    all-one (`0xff`), repeated-byte, small-integer, or common placeholder seeds.

`unseeded_rands_ec.lzma` maps the 64 least significant bits of $x$
(`x mod 2^64`) to the corresponding private scalar $d$. Each key is checked
via an $O(1)$ dictionary lookup followed by exact point multiplication
$d \cdot G = P$, ensuring zero false positives and recovering $d$.

## Aggregate Checks

### CheckECKeySmallDifference

Checks whether any two public keys $P$ and $Q$ on the same curve have
private keys that differ by a small non-zero integer (`SEVERITY_HIGH`), with a
default bound of `max_diff = 2**16` (`65,536`):

$$P - Q = k \cdot G \quad \text{with } 0 < |k| < \text{max_diff}.$$

While finding $P - Q = k \cdot G$ does not immediately reveal the individual
private keys $d_P$ and $d_Q$, it proves that the two keys were generated by
a severely flawed or correlated process (such as a shared counter or adjacent
1-second timestamp seeds), and compromising either key immediately compromises
the other.

`EcCurve.BatchDLOfDifferences` compares a batch of $N$ target `points` against
both each other and an optional list of $M$ previously tested `other_points`
in time $O((N + M) \sqrt{\text{max_diff}})$:

*   **C++ L2-sliced multi-target BSGS (`EcBatchEngine.DiffBatchDL`):** By
    default, deduplicates identical input points in-place, selects baby-step
    radius $h = \lfloor \sqrt{\text{max_diff}} / 2 \rfloor$ (exploiting pair
    symmetry to test only $0 < k < \text{max_diff}$ when `other_points` is
    empty, or $\lfloor \sqrt{\text{max_diff} / 2} \rfloor$ otherwise) and
    giant-step stride $m = 2h + 1$, inserts baby steps $Q \pm b \cdot G$
    into bounded L2-sliced `6`-byte open-addressed hash tables (tiling batches
    exceeding 36M baby-step entries), and streams batched giant-step probes.
*   **Pure-Python fallback:** When the C++ extension is unavailable, selects
    among direct pairwise lookup, single-pass hash-keyed BSGS, and 128 MiB
    `uint32` blocked-Bloom BSGS so peak memory stays bounded even on large
    batches.
